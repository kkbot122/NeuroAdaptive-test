# NeuroLearn Security & Privacy — Phase 6

Threat-model coverage against the paper's five named classes (§VIII), plus
data-governance controls beyond them. Every claim below states what is
tested and what residual risk remains — this document does not claim the
system is secure, only what has been checked and how.

## Table VI — Residual risk by threat class

| Class | Mitigation | Test coverage | Residual risk |
|---|---|---|---|
| T1 — Cross-user access | Owner filter inside every query (Phase 1 convention, `get_owned()` pattern); 404 not 403 everywhere checked | Extensive pre-existing coverage across every module (courses, documents, chunks, curriculum, mastery, adaptation, tutor) + Phase 6 additions for the cross-*course*-same-owner case (`tests/security/test_t1_cross_course.py`) | Coverage is per-endpoint, not exhaustive by construction (no automated fuzzer walks every route). A new endpoint added later could reintroduce the bug class if it doesn't follow the `get_owned()` convention — this is a code-review discipline, not something this test suite can catch structurally. |
| T2 — Malicious/malformed uploads | Magic-byte signature check, extension allowlist, 25MB size cap, page-count cap (500), encrypted-PDF detection, random on-disk filenames, owner-scoped download-only serving | `tests/unit/test_magic_bytes.py`, `tests/unit/test_extraction_t2_security.py` (page-count-bomb, encrypted PDF) | **No malware/antivirus scanning exists** — explicitly not built, per the mandate's own permission to state this plainly rather than skip it silently; would need ClamAV or an equivalent service this deployment doesn't run. No true decompression-bomb detector — the size cap bounds worst-case blast radius but doesn't detect the specific structure. DOCX/PPTX are rejected outright (unsupported), not a gap for this sprint's frozen scope. |
| T3 — Indirect prompt injection | Untrusted content delimited + labeled in all three extraction-family surfaces (`core/prompt_safety.py`) and the tutor (`tutor/prompt.py`, pre-existing); model told never to follow embedded instructions or invoke tools from them | Structural: `tests/security/test_t3_injection_labeling.py` proves the literal prompt sent to the model actually delimits every payload in the documented set, across extraction, edge proposal, adjudication, and the tutor. **Live measurement** (`scripts/measure_injection_resistance.py`, real Gemini calls, not fakes): **0/12 attack attempts succeeded** (6 payloads × 2 surfaces, run once against `gemini-3.5-flash-lite`). | **This is a small sample against one model snapshot on one day — not a claim that injection is prevented.** 6 hand-authored payloads is not an adversarial red-team corpus; more sophisticated attacks (payloads blended into plausible-looking course content, multi-turn setup, encoding tricks) were not attempted and would very plausibly find failures a blunt "ignore previous instructions" string does not. A 0% result here should be read as "this specific small test found nothing this time," not as evidence the defense generalizes. Re-run after any prompt change; do not treat this number as static proof. |
| T4 — Fabricated/unsupported claims | Two-tier citation validation (Phase 5, `tutor/validation.py`) applied uniformly: the tutor and lesson-content generation (Phase 9 follow-up) both route through `TutorService.ask()`, so both get the identical tier-1/tier-2 checks. Concept extraction (Phase 2) uses a structurally equivalent check instead — `curriculum/validation.py` requires every `ConceptSource.chunk_id` resolve to a real, owned chunk before a course version can activate — because extraction produces structured `Concept` rows with source links, not free-text claims with inline citations, so the *same* per-claim mechanism doesn't apply, but the *same property* (a cited/sourced thing must really exist and be owned) is enforced. | `tests/unit/test_tutor_validation.py` (tier1/tier2), `tests/service/test_curriculum_validation.py::TestCitationResolution` (fabricated/cross-course chunk references in `ConceptSource`, pre-existing, verified as still covering this case rather than re-implemented) | Tier 2 (semantic entailment) is sampled, not exhaustive (`TIER2_SAMPLE_EVERY = 2`) — an unsampled claim can pass tier 1 and never have its actual truthfulness checked this round. This is a stated, deliberate latency/cost tradeoff from Phase 5, not new to this phase. |
| T5 — Abuse/DoS/cost | Per-user daily AI-call budget (`AIUsageDaily`, 200/day default), per-course regeneration cap (3/day default), per-user burst rate limit (20/60s on generation endpoints), per-user concurrency limit (2 in-flight generations), all returning RFC 7807 `application/problem+json` bodies with a `reset_at` | `tests/security/test_t5_abuse_dos_cost.py` — budget exhaustion, regeneration cap, burst throttling, concurrency rejection and release | **Rate/concurrency limiting is in-process, in-memory state** (`core/rate_limit.py`) — correct for exactly one backend process. A multi-replica production deployment would need a shared store (Redis) for the limit to hold across replicas; documented, not silently assumed away. "Token budget" is approximated as a call count, not true LLM token usage — `GenerationGateway` doesn't surface per-call token counts in this phase. No real alerting infrastructure (PagerDuty/etc.) — cost anomalies are not actively paged on; this is deferred, consistent with the mandate's note that full observability is Phase 10. |
| Privacy — consent/minimization | `User.tracking_consent` (full/minimal); `minimal` short-circuits `LearningEvent` persistence entirely at the events endpoint | `tests/security/test_privacy_and_audit.py::TestConsentDegradesGracefully` — proves the full core loop (create course → upload → generate → mastery report → assess) works with `minimal` consent, and that no `LearningEvent` row is written | `LearningEvent.payload` still stores whatever a *consenting* client sends verbatim (no field-level minimization within an accepted event) — out of scope for this phase; the phase's requirement was a working opt-out, not payload-level scrubbing. |
| Privacy — deletion/retention | `DELETE /me` (`PrivacyService.delete_account`) explicitly, synchronously deletes every course/document/chunk/curriculum/mastery/adaptation/tutor/legacy row a user owns, then the user row | `tests/security/test_privacy_and_audit.py::TestAccountDeletion` — cascade verified against a real multi-table footprint (course, chunk, concept, mastery event, adaptation decision, presentation affinity, AI usage), plus a post-deletion refetch returning 404/401 | Deletion is immediate, not a scheduled/deferred job — stricter than "within N days," not weaker, but there is no async worker (no Celery in this stack) if a future requirement needed deferred/batched deletion instead. Deletion relies on explicit ordered deletes, not DB-level `ON DELETE CASCADE` — a future table added to the schema must be added to `PrivacyService.delete_account` by hand, or it becomes an orphaned-data bug; this is a maintenance obligation, not a one-time fix. |
| Privacy — independent resets | `POST /presentation-affinity/reset` clears only `PresentationAffinity`; `ConceptMastery`/`MasteryEvent` rows for the same user are untouched | `tests/security/test_privacy_and_audit.py::TestPresentationAffinityResetIsIndependentOfMastery` | None identified for this specific, narrow control. |
| Audit | `AuditLog` (actor, action, target_type, target_id, timestamp, extra); written before account deletion executes | `tests/security/test_privacy_and_audit.py` — entry written on deletion request, and confirmed to survive the deletion it describes | Only one action type is audited so far (`account_deletion_requested`) — there is no admin role or quota-override mechanism yet to generate other audit-worthy events; the table is general-purpose and ready for more call sites when those features exist. |

## What this phase does not claim

- **Prompt injection is not "prevented."** The measured attack success rate against a small, hand-authored payload set was 0/12 on one day against one model. No claim is made that this generalizes to a determined attacker, a larger corpus, or a future model version. Re-measure after any change to prompt construction.
- **The system is not "fully secure."** The table above is the actual claim: which threat classes have test coverage, and what is explicitly known to remain open (no malware scanning, in-memory rate limiting that doesn't span replicas, sampled rather than exhaustive semantic citation checking, no field-level telemetry minimization).
- **Malware scanning does not exist.** Stated plainly per the mandate's own instruction to document absence rather than skip it silently.
