# CONTRIBUTING.md

How work enters this repository. Read `AGENTS.md` first if you are an automated
agent; read `SYSTEM_ARCHITECTURE.md` before any change that touches structure.

---

## 1. Branches

Default branch is `main`. Never commit directly to it.

```
feature/<short-slug>     new capability
fix/<short-slug>         defect repair
chore/<short-slug>       tooling, deps, docs, cleanup
refactor/<short-slug>    behaviour-preserving restructure
```

One concern per branch. If a branch needs the word "and" to describe it, split it.

## 2. Commits

Imperative mood, one logical change per commit.

```
fix(content): derive reader identity from session instead of query param
feat(ingestion): add chunker with configurable overlap
chore(deps): convert requirements.txt to UTF-8
```

Do not amend or force-push a branch someone else may have pulled. Never rewrite
`main`.

## 3. Pull requests

A PR must state: what changed, why, how it was verified, and what was *not*
covered. Include migration ids for schema changes.

The PR description must distinguish **what actually ran** from what was reasoned
about. "Confirmed by inspection" is a legitimate claim; presenting it as
"confirmed by execution" is not.

Checklist:

- [ ] Scoped to one concern
- [ ] Tests added at the layers §4 requires
- [ ] Lint and type-check run (or explicitly noted as not runnable, with reason)
- [ ] Alembic migration present for any schema change
- [ ] No hard-coded secret, no fallback default for a security-critical value
- [ ] Ownership enforced server-side on every new path segment
- [ ] No unvalidated claim stated as fact (`AGENTS.md` §7)
- [ ] Conflicts with `AGENTS.md` / `SYSTEM_ARCHITECTURE.md` stated, not resolved silently

## 4. Test layers

Seven layers. A change is expected to touch the layers its blast radius reaches —
not all seven, and not zero.

| Layer | Scope | Where | Required when |
|---|---|---|---|
| **Unit** | One pure function, no I/O | `backend/tests/unit/` | Any new math, transform, or parser. Mandatory for adaptation/mastery formulas. |
| **Repository / service** | One service against a real test DB | `backend/tests/service/` | Any new query or persistence logic. |
| **API** | One endpoint through FastAPI's test client | `backend/tests/api/` | Any new or changed route. Must include an unauthorized-access case. |
| **Contract** | Response shape matches what the frontend consumes | `backend/tests/contract/` | Any change to a response body the UI reads. |
| **Component** | One React component in isolation | `frontend/__tests__/` | Any component with branching render logic. |
| **End-to-end** | A full user journey | `e2e/` | Any change to the sign-in → read → adapt loop. |
| **Evaluation fixtures** | Frozen inputs with expected qualitative properties | `backend/tests/eval/` | Any change to a prompt, retrieval strategy, or grading rule. |

**Every endpoint test must include a negative authorization case** — a caller who
does not own the resource receives 404, not 403, and not the resource.

**Running the backend suite:**

```bash
pip install -r requirements.txt -r requirements-dev.txt
pytest                    # from backend/
```

> **Current reality:** the unit and API layers exist and run (92 tests). The
> repository/service, contract, component, end-to-end and evaluation layers do
> not yet, and the frontend has no runner at all. State plainly in the PR when a
> layer your change touches has no coverage.

## 5. Running things locally

```bash
docker compose up --build          # db + backend + frontend
docker compose exec backend alembic upgrade head
```

Backend expects `backend/.env`; frontend expects `frontend/.env.local`. Both are
gitignored. Never commit either, and never add a secret under a `NEXT_PUBLIC_`
prefix — that inlines it into the browser bundle.

## 6. Migrations

```bash
docker compose exec backend alembic revision --autogenerate -m "short description"
docker compose exec backend alembic upgrade head
```

Review autogenerated migrations by hand — Alembic misses type changes, server
defaults, and constraint renames. Keep the chain single-headed. Never edit a
migration that has been merged; add a new one. Never delete a migration without
explicit approval.

## 7. Ownership tracks

Changes are grouped into tracks so review lands with someone who holds context.
A PR should name its track.

| Track | Covers |
|---|---|
| **Platform** | auth, config, security, migrations, Compose, CI |
| **Ingestion** | upload, extraction, chunking, embedding, indexing, workers |
| **Learning** | concepts, curriculum, assessment, mastery, adaptation |
| **Tutor** | RAG, citations, prompts, provider abstraction |
| **Interface** | Next.js routes, components, client state |
| **Evaluation** | fixtures, harness, analysis |

Cross-track PRs need a reviewer from each track they touch.

## 8. Dependencies

Adding a dependency needs a reason in the PR description. Adding one that
introduces a new class of infrastructure — a queue, a datastore, a vector index —
needs agreement before the PR, because it changes the topology in
`SYSTEM_ARCHITECTURE.md` §15.

Note that `qdrant-client`, `boto3`, and `minio` are already declared but unused;
prefer wiring these up over adding alternatives.

## 9. Issue tracking

If the team is using Linear, one issue per branch and the issue id in the PR
title. This is optional — phase prompts and plain PRs are equally acceptable, and
nothing in this repository depends on an issue tracker being present.
